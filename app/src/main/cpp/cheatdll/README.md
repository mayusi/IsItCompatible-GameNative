# cheatdll — in-game one-tap cheat engine (x86_64 Windows proxy DLL)

This is the cheat engine that powers the one-tap cheats on the Cheats tab. Unlike
`libtrainer.so` (which runs in the Box64/FEXCore **host** and reads `/proc/self/mem`),
this DLL is **Windows x86_64 code that runs INSIDE the game's own process** under
Wine. Memory access is therefore plain in-process pointers — no ptrace, no RPM/WPM,
no SELinux issues, no host/guest boundary.

## How it loads

`CheatStager.kt` (Kotlin) copies our proxy `d3dx9_43.dll` next to the game exe at
launch and sets `WINEDLLOVERRIDES=d3dx9_43=n,b`, so the game loads our proxy, then
starts the cheat thread in `cheat.c`.

**Why d3dx9_43 and NOT dinput8 (device-proven):** on arm64ec Proton, Wine FORCES
`dinput8`/`winmm`/`xinput`/`version` + all core DLLs to `: builtin` (arm64ec hybrid
builtins); the loader ignores any disk PE in those slots — an x86_64 proxy at
`system32\dinput8.dll` with `*dinput8=n,b` STILL loaded `: builtin` on-device and our
DllMain never ran. But Wine loads `d3d9`/`d3dx9_43`/`d3dcompiler_43`/`MSVCR100`/
`MSVCP100` `: native` from disk on the same launch. `d3dx9_43` is a DX9 HELPER lib OFF
the DXVK render path (DXVK owns `d3d9`/`dxgi`, untouched), so replacing it does NOT
break rendering. The repo already ships `d3dx9_43=native,builtin` for game 413420
(gamefixes/registry.json), proving the native override works on this exact stack.

**Complete forwarding (no missing-export crash):** `d3dx9_43` has ~329 exports.
`proxy.c` writes none by hand — instead `d3dx9_43.dll` is linked with `d3dx9_43.def`
(generated by `build_def.py` from the genuine lib's export table), where EVERY export
is a forwarder to `d3dx9_43_real.<Name>`. `CheatStager` stages the prefix's genuine
`system32\d3dx9_43.dll` next to the exe as `d3dx9_43_real.dll`, so the loader resolves
all 329 forwarders into the real implementation while our DllMain runs the engine.
No `system32` overwrite is needed (d3dx9_43 is not a builtin — the exe-dir copy wins).

## How it's driven

The Android UI (`ProxyCtrl.kt`) writes one command line to `<gameDir>/cheat_ctrl.txt`;
the DLL polls it (~400ms, de-dupes by content) and writes acks to `cheat_out.txt`.

Main command — generic pointer-chain freeze (catalog-driven, works for ANY game):

    chain=<id>|<module>|<basehex>|<off1,off2,...>|<valoffhex>|<vtype i32|u32|f32>|<mode lit|max>|<valbits>

Resolution (standard Cheat-Engine semantics): `ptr = *(moduleBase + base)`, then for
each offset `ptr = *(ptr + off)`, then `valueAddr = ptr + valueOffset`. `mode=max`
writes `*valueAddr = *(maxField)` (maxField at valueAddr - valueOffset + maxOffset);
`mode=lit` writes the literal. Disable: `chainoff=<id>` / `chainclear`.

Also includes a universal value scanner for the "make your own cheat" path:
`snap`, `inc`/`dec`/`chg`, `scani=`/`scanf=`, `nexti=`/`nextf=`, `freezei=`/`freezef=`,
plus diagnostics `readrel=`/`readabs=`/`dmc3diag`/`orbscan=`.

AOB (signature) scan — needed by imported Cheat-Engine `.CT` tables:

    aobscan=<id>|<pattern-hex-with-?? wildcards>|<signed-offset>

Scans committed/readable memory (reusing the value-scanner's region walk + the
same committed/readable/non-guard, skip-&gt;256MB filter — code/executable pages are
included so code signatures resolve), finds the first match, applies the signed
byte offset, and writes the resolved address back as
`[aob] id=<id> found=0x<addr>` (or `[aob] id=<id> notfound`). The Kotlin
`ProxyCtrl.aobScan()` polls that line on the same round-trip channel as the scanner.

## Build

64-bit only (the guest games are x64 PEs). MinGW-w64 (installed on the dev machine).
First regenerate the forwarder def (only needed if the genuine lib changed):

    gendef /c/Windows/System32/d3dx9_43.dll      # -> d3dx9_43.def dump
    # rename the dump to d3dx9_43_real_src.def, then:
    python build_def.py                          # -> d3dx9_43.def (329 forwarders)

Then link the proxy WITH the def (the def supplies the entire export surface). The
build is deliberately **CRT-free** so our `DllMain` actually runs (see below):

    x86_64-w64-mingw32-gcc -shared -O2 -s -nostartfiles -e DllMain -nodefaultlibs \
        -o d3dx9_43.dll proxy.c cheat.c d3dx9_43.def -lmsvcrt-os -lkernel32

**Why these flags (device-diagnosed):** the WinLibs toolchain is *UCRT* flavour, so a
normal build imported `api-ms-win-crt-*` apisets and carried a `.tls` CRT directory,
with the PE entry at `DllMainCRTStartup -> _CRT_INIT -> DllMain`. On arm64ec Wine that
UCRT `_CRT_INIT` couldn't complete in the emulated x86_64 context and returned early,
so our `DllMain` body (proof file + engine + fling chain-load) **never ran** even though
the DLL mapped `: native` with a correct entry point. The fix is two parts:
`-nostartfiles -e DllMain` makes `DllMain` the **direct PE entry point** (no
`_CRT_INIT` in front of it), and `-nodefaultlibs ... -lmsvcrt-os` binds the C-library
calls to Wine's **builtin `msvcrt.dll`** (always present, no apiset/CRT init) instead of
the UCRT apisets. NOTE: link `-lmsvcrt-os`, NOT `-lmsvcrt` — on this UCRT toolchain
`-lmsvcrt` is an alias bundle that still forwards to the apisets. `crt_msvcrt_shim.h`
(included by `proxy.c`/`cheat.c`) maps the C99 `snprintf` the sources use onto msvcrt's
`_vsnprintf` (msvcrt exports only `_snprintf`/`_vsnprintf`). Verify the result imports
**only `kernel32` + `msvcrt.dll`** (no `api-ms-win-crt-*`, no `ucrtbase`, no `.tls`):

    objdump -p d3dx9_43.dll | grep 'DLL Name'      # -> KERNEL32.dll, msvcrt.dll only

The resulting `d3dx9_43.dll` is committed here AND copied to
`app/src/main/assets/cheatdll/d3dx9_43.dll` (the APK asset that ships to the device).
After editing `cheat.c`/`proxy.c`, rebuild and re-copy the asset before building the APK.

## Per-game carrier / fallback chain

The carrier defaults to `d3dx9_43` (DX9). For non-DX9 games, build the same source as a
different proxy name the game DOES import — the intended fallback chain is
`d3dx9_43` (DX9) → `d3dx11_43` (DX11) → `d3dcompiler_47` → (last resort) a `dxgi`
chain-forward carrier — each with its own generated forwarder def, selected per-game via
`TrainerEntry.proxyName` / the registry. Only the `d3dx9_43` carrier binary ships today.
